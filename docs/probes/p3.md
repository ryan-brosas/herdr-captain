# Probe P3: `hc` `0.1.22` behaviour observed in live use

**Date:** 2026-11-27
**Status:** COMPLETED WITH GAPS AND DESIGN CHANGES (observed in live use; `Not observed` items and section 8 verdicts below)
**Scope:** Issue `herdr-captain#5`, [docs/proof-plan.md](../proof-plan.md) (P3 row), [docs/architecture.md](../architecture.md#8-crash-windows-and-recovery) section 8, and [ADR-0002](../adr/0002-recovery.md). Terms follow [CONTEXT.md](../../CONTEXT.md).

## Method and why no scratch core was used

[docs/proof-plan.md](../proof-plan.md) and the original text of issue `herdr-captain#5` planned to run probe P3 inside a scratch `hc` core (`HC_SESSION` and a scratch XDG state root). A pre-run plan check found that a scratch core could not be kept safely apart from a live core on the same machine, so the ticket was held as `risky`.

With the repository owner's approval, the Captain's operator observed the target behaviours on 2026-11-27 on `hc` `0.1.22` through ordinary `hc` use in a live session:

- **Six short-lived stand-in terminals** (`sleep` and `sh` loops) with top-level launches using `--no-parent --no-notify`. Preflight found `0` terminals carrying `<prefix>-`. After the run, all six probe terminals were removed; both the script's cleanup check and an independent `hc ls --all` found `0` terminals carrying `<prefix>-` left (`overall 0`).
- **Read-only inspection and ordinary-use notes** from real agent terminals in the same run: read-only `hc get --json` outputs for six agent terminals (two Antigravity `implementer` launches, two Codex `reviewer` launches, and two Codex `validator` launches) plus Captain's notes `N1` to `N5`.
- **Read-only `hc` documentation commands:** `hc --skill` and `hc schema --json` on `hc` `0.1.22`.
- **Commands not run:** no `hc server`, `hc update`, or `hc machine` command was run (`N4`). No probe script or `probes/p3/` directory was added; these records are the proof for this ticket.

All raw receipts stay private. Terminal IDs, the name prefix, scratch paths, other live terminals' names, and redacted app labels are replaced with the placeholders from the sanitised observations: `<prefix>`, `<scratch>`, `<named>`, `<parent>`, `<outlive-child>`, `<default-child>`, `<report>`, `<no-id>`, `<t>`, `<name>`, and `<agent app>`.

## Behaviour 2: `first_message.sent` for ready and late-ready programs

**Sources:** Captain's notes `N1`, `N4`, `N5`; observations section `Fields on six real agent terminals of this run` (`hc get --json`, read-only); `hc --skill` (`Delegate a task`); `hc schema --json` (`FirstMessage`, `RunResult.properties.first_message`, `Terminal.properties.first_message`).

### Recorded outputs and notes

Read-only `hc get --json` on six real agent terminals from this run (two Antigravity `implementer` terminals that hit a folder-trust dialog at launch, plus two Codex `reviewer` and two Codex `validator` terminals that did not):

```json
{"template":"implementer","state":"live","status":{"app":"antigravity","state":"working"},"turn":4,"first_message":{"reason":"<t> is blocked (permission); typing would answer its dialog; read its screen first (hc read <t>), or --force","sent":false},"die_with_parent":true,"reported":true}
{"template":"implementer","state":"live","status":{"app":"antigravity","state":"working"},"turn":3,"first_message":{"reason":"<t> is blocked (permission); typing would answer its dialog; read its screen first (hc read <t>), or --force","sent":false},"die_with_parent":true,"reported":true}
{"template":"reviewer","state":"live","status":{"app":"codex","state":"done"},"turn":4,"die_with_parent":true,"reported":true}
{"template":"reviewer","state":"live","status":{"app":"codex","state":"idle"},"turn":4,"die_with_parent":true,"reported":true}
{"template":"validator","state":"live","status":{"app":"codex","state":"done"},"turn":4,"die_with_parent":true,"reported":true}
{"template":"validator","state":"live","status":{"app":"codex","state":"idle"},"turn":5,"die_with_parent":true,"reported":true}
```

Manual and schema facts (`hc` `0.1.22`):

- `hc --skill` (`Delegate a task`): "Check `first_message.sent` in a launch with a task. If false, the task was NOT sent; `hc get <t>` keeps `first_message: {sent: false, reason}` for later inspection, even after the core restarts."
- `hc schema --json` `RunResult.properties.first_message`: `"Template runs: whether the first message went in."`
- `hc schema --json` `Terminal.properties.first_message` (returned by `hc get`): `"A template first message that was not sent; retained for later inspection."`
- `hc schema --json` `FirstMessage`: required `sent` (`boolean`); optional `reason` (`string | null`, `"Why it was not sent."`), `started` (`boolean | null`, `"Whether the agent started working on it (see terminal.send)."`), and `turn` (`uint64 | null`, `"The turn when it went in (see terminal.send)."`).

### What this shows

- **Observed (`sent: false`):** In 4 of 4 first launches of the `implementer` template in newly created worktrees (3 in `N1` plus 1 in `N5`), the launch receipt reported `first_message.sent: false` with the permission-blocked reason, and the task was not sent.
- **Observed (`hc get` retention):** In 2 of 2 live `implementer` terminals inspected hours later (observations agent terminals; `N1`), `hc get --json` still returned `first_message: {sent: false, reason}`. That remained true after the Captain cleared the dialog, sent the task via `hc send`, and the terminals reached `turn: 3` and `turn: 4` while `working`. On the fourth launch (`N5`), `hc get` right after clearing the dialog also returned `"first_message":{"sent":false}`.
- **Observed (`hc get` on trusted Codex launches):** In 4 of 4 Codex launches (`reviewer` and `validator`) that did not stop at a trust dialog, later `hc get --json` omitted `first_message` (recorded as `first_message: null` in `N1`). That matches `hc schema --json` `Terminal.properties.first_message`, which retains only a template first message that was **not** sent.
- **Not observed:** A launch receipt (`RunResult`) with `first_message.sent: true` was not saved for those four Codex launches (`N1`), and a first message to a program that becomes ready late was not run (`N4`). See `Not observed`.
- **Design implication:** Post-crash readback via `hc get` cannot rely on seeing `first_message.sent: true`, because `Terminal.first_message` does not store sent messages. Also, a later reconciliation must not mistake a retained `first_message.sent: false` on `hc get` for a failure of a subsequent `hc send`.

### Full-screen history-read side effect (`N3`)

- Three times in this run, `hc read <t> --lines N` with `N > 0` on an idle terminal of agent program B left a mouse escape sequence typed into that program's prompt, for example `[<65;101;61M` (`N3`).
- `hc schema --json` (`ReadResult.properties.how`) describes `"stitched"` as `"a full-screen app, read by scrolling it"`.
- Observed consequences (`N3`, `N2`): once the next `hc send` appended the task to that stray text; once `hc send` returned `started: false` and submitted nothing (`N2`, fifth bullet).
- Reads with `--lines 0` (screen only) on the same terminals were not followed by stray text in this run (`N3`).

### What this shows

- **Full read when window is large enough:** In 1 of 1 finished non-`--rm` stand-in terminal (`c4-read-1000-json`), `hc read <report> --lines 1000 --json` returned all 401 lines (`report line 1 of 400` through `REPORT-END`) with `complete: true` and `how: "history"`.
- **Default and `--lines` sizing:** `c7-read-0-text` (`hc read <report>`) returned 120 lines (the default headless height of 120 rows documented in `hc schema --json` `terminal.run` `size`), and `c5`/`c6` (`--lines 50`) returned 170 lines (`120` screen rows plus `50` history lines, matching `hc schema --json` `terminal.read` `lines`: `"Lines of history above the screen."`).
- **`complete: true` does not prove the whole report was returned (design change needed):** In `c5-read-50-json`, lines 1 to 231 of the 400-line report were missing, yet `hc read` still returned `complete: true`. `hc schema --json` (`ReadResult.properties.complete`) defines `complete` as `"False when part of what was asked for may be missing."` It signals only whether the requested slice (`screen + --lines`) could be fetched (for instance, `hc --skill` and `ReadResult.properties.why` note that reading history while a full-screen app is `working`, `blocked`, or `error` returns only the screen with `complete: false` and `why` set to that status). Truncation caused by a too-small `--lines` bound is **not** flagged by `complete`.
- **Two design changes for capture and readback:**
  1. Never treat `ReadResult.complete === true` alone as proof that a full report or verdict was captured. Require `complete === true` and `Terminal.screen === "exact"` (`hc schema --json` `Terminal.screen`: `"exact"`, or `"inexact"` after a core crash). Verify completeness independently too: read report files from disk when the worker can write files (`hc --skill` advises writing long answers to a file). For read-only verdicts captured from `hc read`, require explicit start/end framing markers or confirm returned lines fall below the requested window.
  2. Use `hc read --lines 0` (screen only) when inspecting live full-screen agent terminals that may receive later `hc send` calls (`N3`). Reserve `--lines N > 0` for finished terminals or terminals killed immediately after capture.
- **Not observed:** `ReadResult.complete: false`, `Terminal.screen: "inexact"`, and `hc read` on a finished full-screen agent terminal (see `Not observed`).

Then `hc get` returned `{"state":"live","status":{"app":"antigravity","state":"idle"},"turn":0,"first_message":{"sent":false}}`.

### Exact field comparison (`hc` `0.1.22`)

| Surface | Schema | `turn` | `status` | Other key status/delivery fields |
|---|---|---|---|---|
| `hc get --json` | `Terminal` | `uint64` (`"Goes up each time the status leaves working."`) | `null` or `Status` object (`{ state, app?, kind?, msg?, progress?, title? }`) | `state` (`"live"` or `"finished"`), `reported` (`boolean`), `exit_code`, `signal`, `reason`, `first_message` (unsent template message only) |
| `hc send --json` | `SendResult` | `uint64` (`"The turn when the text went in."`) | `string \| null` (`"The program's status word when the text went in (null: it never said)."`) | `started` (`boolean \| null`: `"Whether it went working within a few seconds; null when it doesn't report status, so nobody can tell."`), optional `wait` (`WaitResult \| null`) |
| `hc keys --json` | `KeysResult` | `uint64` | `string \| null` | (Observed in `N1` and `N5`: `{"status":"blocked","turn":0}`) |

### What this shows

- **`status` has different types across commands:** `hc get --json` returns `status` as a JSON object (`status.state`, plus `app`, and `kind`/`msg` when blocked) or `null` for plain programs (`a2`, six agent terminals, `N5`; `hc schema --json` `Status`). `hc send --json` returns `status` as a plain string word or `null` (`a5`, `N1`, `N2`; `hc schema --json` `SendResult`). Adapter code must read `status?.state` on `hc get` and never compare the `hc get` object directly to `"blocked"`.
- **Turn timing requires a design change for ambiguous-send readback:** Across the 5 `started: true` agent sends in `N2` (plus `a5`/`a6` on a plain program), the send receipt's `turn` matched `hc get` before the send in 2 of 2 pre-send checks (samples 4 and 5) and during `working` in 4 of 4 during-turn checks (samples 2 to 5). After the turn ended, `hc get` showed `turn + 1` in 3 of 3 post-turn checks (samples 2, 3, and 6). That matches `hc schema --json` `Terminal.properties.turn` (`"Goes up each time the status leaves working."`). During post-crash send reconciliation, `turn === preSendTurn` while `status?.state === "working"` does **not** prove the send failed. Wait for `working` to end before checking `turn > preSendTurn`, and still never blind resend.
- **`started: false` and `started: null` stay ambiguous:** `started: null` occurred in 1 of 1 send to a non-reporting program (`a5-send-plain`). `started: false` occurred both when text failed to land on `done` (3 of 3 early sends on agent program A, `N2`) and when stray prompt text blocked submission (1 send on agent program B, `N2`/`N3`), while 2 of 2 later sends on `done` to agent program A returned `started: true`. Keeping `started: false` and `started: null` in `uncertain` until readback confirms (never blind resending) holds.

## Behaviour 7: Launch-time folder-trust dialog and open design question

**Sources:** Captain's notes `N1`, `N5`; observations section `Fields on six real agent terminals of this run`; `hc --skill` (`Delegate a task`, `Status, recovery, and cleanup`); `hc schema --json` (`FirstMessage`, `Status`, `terminal.send`).

### What was observed

- **Launch receipt (`N1`, `N5`):** In 4 of 4 first launches of the `implementer` template (Antigravity) in newly created worktrees (3 in `N1` plus 1 in `N5`), the launch receipt reported `first_message.sent: false` with `reason: "<t> is blocked (permission); typing would answer its dialog; read its screen first (hc read <t>), or --force"`. In `N5` (1 of 1 where extra launch fields were recorded), the receipt also carried `turn: 0` and `template: implementer`. The launch task was **not delivered** in all 4 launches.
- **Parent notification (`N1`, `N5`):** In 4 of 4 blocked launches, the core typed `<t> <name> is blocked (permission). See: hc read <t>` into the parent terminal.
- **`hc get` during the dialog (`N5`):** In 1 of 1 launch where `hc get` was recorded while the dialog was open (`N5`), `status` was `{"app":"<agent app>","kind":"permission","msg":"Trust this folder?","state":"blocked"}` and `turn` was `0`. That confirms `hc schema --json` `Status`: a `blocked` status object can include `kind` (`"permission"`) and `msg` (`"Trust this folder?"`) beside `state`.
- **Screen and manual recovery in this run (`N1`, `N5`):** `hc read <t>` showed the folder-trust dialog naming the worktree path, with `"Yes, I trust this folder"` highlighted and `"No, exit"` below it (`N5`; `"Yes"` highlighted in `N1`). In this run, the Captain accepted the dialog with one key press (`enter` in `N5`) only after reading the screen and verifying it was the trust dialog for a worktree the Captain had created. The key press returned `{"status":"blocked","turn":0}` (`N1`, `N5`). `hc get` then showed `status.state: "idle"` (`N1`; exact JSON in `N5`: `{"state":"live","status":{"app":"antigravity","state":"idle"},"turn":0,"first_message":{"sent":false}}`). In `N1`, sending the task via `hc send` returned `{"started":true,"status":"idle","turn":0}` and moved status to `working`.
- **Persistence in `hc get` (`N1`, observations agent terminals):** Hours later, 2 of 2 live `implementer` terminals still reported `first_message: {sent: false, reason}` in `hc get --json` while `working` at turns `3` and `4`.
- **Second agent program comparison (`N1`, observations agent terminals):** Codex asked for trust once for the repository root rather than once per worktree. In 4 of 4 later Codex launches (`reviewer` and `validator`) in trusted folders, no trust dialog appeared (launch receipts were not saved; later `hc get --json` omitted `first_message` / showed `null`).

### Current rule and open design question for the repository owner

[docs/architecture.md](../architecture.md#8-crash-windows-and-recovery) section 8 keeps the current rule unchanged: any `blocked` prompt escalates to the user, with no `hc send --force` and no automated `hc keys`.

**Open design question for the repository owner:** Should a launch-time folder-trust dialog (`status.state === "blocked"`, `kind === "permission"`) for a worktree the Captain created be cleared as launch readiness after reading the screen (`hc read --lines 0`) and confirming the worktree path and prompt text? Every other `blocked` prompt would still escalate to the user. The alternative is to keep escalating every `blocked` prompt, including worktree folder-trust dialogs.

## Not observed

The items below were not observed in these records and are not assumed:

1. **A first message to a program that becomes ready late:** Not run (`N4`). Testing a template launch against a stand-in program requires writing a template file into `hc`'s real templates folder (per `hc --skill` `Delegate a task`), which was off limits in a live session.
2. **`hc wait --children` with `HC_TERMINAL_ID` unset and no terminal named:** Not run (`d1`, `N4`). Without a named terminal, it could have fallen back to the caller's own terminal and marked the caller's own child news as seen.
3. **A launch receipt (`RunResult`) with `first_message.sent: true`:** Not recorded (`N1`). The launch receipts for the four Codex launches in trusted folders were not saved; only `hc get --json` after the fact was read, and `Terminal.properties.first_message` retains only unsent template first messages.
4. **Whether child replies to `$HC_TERMINAL_ID` are lost after the parent exits or is removed:** No step ran `hc send` targeting a finished or removed parent terminal. `hc schema --json` (`terminal.send` errors) and `hc --skill` document `finished` (exit `11`) and `not_found` (exit `3`) errors rather than silent delivery, so reconciliation must read worker state and output directly instead of relying on child replies to a dead Captain address.
5. **`hc label` setting and `hc ls` label filtering:** No `hc label` or `hc ls` label-filter command was run. `hc schema --json` documents `terminal.label` and `terminal.list` `labels` filtering, and `labels` appeared in the `hc get --json` key list.
6. **Additional boundaries outside the observed commands:**
   - `hc wait <parent> --children` after `<parent>` has been removed with `hc rm` (`b7` and `b8` tested a finished non-`--rm` parent still in the registry).
   - Parent death by `SIGKILL` or OS crash (`b1` to `b6` tested normal parent exit `0`) and `hc keep` shell replacement (`hc --skill`, `hc schema --json` `Terminal.keep` / `Terminal.reason`).
   - `ReadResult.complete: false` (such as reading history of a `working`, `blocked`, or `error` full-screen app, or `Terminal.screen: "inexact"` after a core crash) and `hc read` on a finished full-screen agent terminal (`c1` to `c7` used a plain `sh` script).
   - Direct `hc send` refusal on a `blocked` terminal (exit `9` documented in `hc --skill` and `hc schema --json` `terminal.send`; in `N1` and `N5`, the launch itself refused the first message and `hc send` ran only after status became `idle`).
   - Reusing the name of a finished non-`--rm` terminal on a new `hc run` (`a4-run-duplicate-name` tested a live holder only).
   - Any `hc server`, `hc update`, or `hc machine` command (`N4`).
