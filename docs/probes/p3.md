# Probe P3: `hc` `0.1.22` behaviour observed in live use

**Date:** 2026-11-27
**Status:** COMPLETED WITH GAPS AND DESIGN CHANGES (observed in live use; `Not observed` items, note limits, and section 8 verdicts below)
**Scope:** Issue `herdr-captain#5`, [docs/proof-plan.md](../proof-plan.md) (P3 row), [docs/architecture.md](../architecture.md#8-crash-windows-and-recovery) section 8, and [ADR-0002](../adr/0002-recovery.md). Terms follow [CONTEXT.md](../../CONTEXT.md).

## Method and why no scratch core was used

[docs/proof-plan.md](../proof-plan.md) and the original text of issue `herdr-captain#5` planned to run probe P3 inside a scratch `hc` core (`HC_SESSION` and a scratch XDG state root). A pre-run plan check found that a scratch core could not be kept safely apart from a live core on the same machine, so the ticket was held as `risky`.

With the repository owner's approval, the Captain's operator observed the target behaviours on 2026-11-27 on `hc` `0.1.22` (step `v`: `hc --version`, exit `0`, output `hc 0.1.22`) through ordinary `hc` use in a live session:

- **Six stand-in terminals** (`sleep` and a shell loop). Four top-level launches used `--no-parent --no-notify` (steps `a1`, `a4`, `b1`, and `c1`; `a4` failed by design with exit `1` and created nothing). The two children in `b1` were started by `<parent>`'s own shell, one with `--outlive-parent --no-notify` (`<outlive-child>`) and one with `--no-notify` (`<default-child>`). Step `d3` used `--no-notify` only (no `--no-parent`), with `HC_TERMINAL_ID` unset. Preflight found `0` terminals carrying `<prefix>-`.
- **Mid-run listing and post-run cleanup:** Step `c8-ls-all` (`hc ls --all --json`, exit `0`) ran mid-run (after `c7`, before `d2`, before any terminal was removed) and is **not** cleanup evidence. After the last step, the script's cleanup check counted `0` terminals carrying `<prefix>-` left (`cleanup` note, `overall 0`). In Captain's note `N6` (no saved raw outputs), six follow-up `hc get <t> --json` calls on the six stand-in addresses each exited `3`, and the scratch folder no longer existed.
- **Read-only inspection and notes from real agent terminals:** Six saved `hc get <t> --json` reads (`e2-get-own-1` to `e2-get-own-6`) ran in the same run, with exit `0` in 6 of 6 and `rows: 120` in 6 of 6. They cover two Antigravity `implementer` terminals, two Codex `reviewer` terminals, and two Codex `validator` terminals. Captain's notes `N1` to `N7` record ordinary use from the same run.
- **Read-only `hc` documentation commands:** `e1-schema` (`hc schema --json`, exit `0`, source of the documented shapes) and `hc --skill` on `hc` `0.1.22`.
- **Commands not run:** no `hc server`, `hc update`, or `hc machine` command was run (`N4`). No probe script or `probes/p3/` directory was added; these records are the proof for this ticket.

All raw receipts stay private. Terminal IDs, the name prefix, scratch and worktree paths, and other live terminals' names are replaced with the placeholders from the sanitised records: `<prefix>`, `<scratch>`, `<worktree>`, `<named>`, `<parent>`, `<outlive-child>`, `<default-child>`, `<report>`, `<no-id>`, `<t>`, and `<name>`.

Records of real agent terminals stay private with the owner. For them, this document gives command shapes, recorded exit codes, counts, and field values. It gives no verbatim output and no verbatim receipt. Independent validation checked those counts and field values against the private records.

## Behaviour 2: `first_message.sent` for ready and late-ready programs

**Sources:** Observations steps `e2-get-own-1` to `e2-get-own-6`, `e1-schema`; Captain's notes `N1`, `N4`, `N5`, `N7` (see `Limits of the Captain's notes`); `hc --skill` (`Delegate a task`); `hc schema --json` (`FirstMessage`, `RunResult.properties.first_message`, `Terminal.properties.first_message`).

### Agent `hc get` summary and schema text

- **`e2-get-own-1` to `e2-get-own-6`** (`hc get <t> --json`, once for each of six real agent terminals of this run; exit `0` in 6 of 6; `rows: 120` in 6 of 6):

| Terminals | Command shape and exit | `first_message` | Other fields seen |
|---|---|---|---|
| 2 Antigravity `implementer` terminals (`e2-get-own-1`, `e2-get-own-2`; from `N1`, hit a folder-trust dialog) | `hc get <t> --json` (exit `0` in 2 of 2) | Present in 2 of 2: `first_message.sent: false`, `first_message.reason` set to permission-block message | `template: "implementer"`, `state: "live"`, `status.app: "antigravity"`, `status.state: "working"`, `die_with_parent: true`, `reported: true`, `rows: 120`, non-zero `turn` |
| 4 Codex terminals (`e2-get-own-3` to `e2-get-own-6`; 2 `reviewer`, 2 `validator`; did not hit a folder-trust dialog) | `hc get <t> --json` (exit `0` in 4 of 4) | Omitted in 4 of 4 | `template: "reviewer"` or `"validator"`, `state: "live"`, `status.app: "codex"`, `status.state: "done"` or `"idle"`, `die_with_parent: true`, `reported: true`, `rows: 120`, non-zero `turn` |

Manual and schema facts (`hc` `0.1.22`, step `e1-schema`, `hc schema --json`, exit `0`; `hc --skill`):

- `hc --skill` (`Delegate a task`): "Check `first_message.sent` in a launch with a task. If false, the task was NOT sent; `hc get <t>` keeps `first_message: {sent: false, reason}` for later inspection, even after the core restarts."
- `hc schema --json` `RunResult.properties.first_message`: `"Template runs: whether the first message went in."`
- `hc schema --json` `Terminal.properties.first_message` (returned by `hc get`): `"A template first message that was not sent; retained for later inspection."`
- `hc schema --json` `FirstMessage`: required `sent` (`boolean`); optional `reason` (`string | null`, `"Why it was not sent."`), `started` (`boolean | null`, `"Whether the agent started working on it (see terminal.send)."`), and `turn` (`uint64 | null`, `"The turn when it went in (see terminal.send)."`).

### What this shows

- **Observed (`sent: false` across 6 `implementer` launches in newly created worktrees):**
  - `N1` records 3 of 3 first launches of the `implementer` template in worktrees created with `git worktree add`, each reporting `first_message.sent: false`. Two of those three terminals were still live during P3 and are backed by saved `hc get` steps `e2-get-own-1` and `e2-get-own-2` (exit `0`). The third had been removed and rests on `N1` alone. Exact `hc run` commands and exit codes were not saved.
  - `N5` records a 4th `implementer` launch in a newly created worktree (note only, no saved raw receipt; command `hc run --bg --json --name <name> --cwd <worktree> implementer "<task>"`, exit `0`) returning `first_message.sent: false`.
  - `N7` records a 5th and 6th `implementer` launch in newly created worktrees (note only, no saved raw receipts; same `hc run` command, process exit codes not recorded), both returning `first_message.sent: false`.
- **Observed (`hc get` retention):** In 2 of 2 live `implementer` terminals checked hours later (`e2-get-own-1`, `e2-get-own-2`, exit `0`; `N1`), `hc get --json` still returned `first_message.sent: false` and a `first_message.reason` string. That held even after the Captain cleared the dialog, sent the task via `hc send`, and both terminals were `working` on later turns. In `N5` (note only, `hc get <t> --json`, exit `0`), `hc get` right after clearing the dialog also returned `first_message.sent: false`.
- **Observed (`hc get` on trusted Codex launches):** In 4 of 4 Codex terminals (`e2-get-own-3` to `e2-get-own-6`, exit `0`; `N1`), `hc get --json` omitted `first_message` (described as `first_message: null` in `N1`). That matches `hc schema --json` `Terminal.properties.first_message`, which retains only a template first message that was **not** sent.
- **Not observed:** A launch receipt (`RunResult`) with `first_message.sent: true` was not saved for those four Codex launches (`N1`), and a first message to a program that becomes ready late was not run (`N4`). See `Not observed`.
- **Design implication:** Post-crash readback via `hc get` cannot rely on seeing `first_message.sent: true`, because `Terminal.first_message` does not retain sent messages. Also, a later reconciliation must not mistake a retained `first_message.sent: false` on `hc get` for a failure of a subsequent `hc send`.

- Finished non-`--rm` lookups by name vs address:
  - `b4-get-parent-by-name-after` (`hc get <prefix>-parent --json`, exit `0`) matched `b4-get-parent-after` (`hc get <parent> --json`, exit `0`); outputs shown under Behaviour 1.
  - `c3-get-finished-by-name` (`hc get <prefix>-report --json`, exit `0`) matched `c3-get-finished-by-address` (`hc get <report> --json`, exit `0`); outputs shown under Behaviour 4.

### What this shows

- In 1 of 1 live lookup (`a2-get-by-name` vs `a3-get-by-address`) and 2 of 2 finished non-`--rm` lookups (`b4-get-parent-by-name-after` vs `b4-get-parent-after`; `c3-get-finished-by-name` vs `c3-get-finished-by-address`), `hc get <name> --json` exited `0` and returned the same terminal fields as `hc get <address> --json`. Top-level keys of `hc get --json` include `address` (observations line 8; `hc schema --json` `Terminal.required`), so a name lookup recovers the address.
- In 1 of 1 duplicate-name launch while the holder was live (`a4-run-duplicate-name`), `hc run` failed with exit `1` and `error.kind: "name_taken"` (no terminal address returned). Reusing a finished terminal's name was not tested.
- **Schema constraint requiring a design change:** `hc schema --json` (`terminal.run`, param `name`) states: `"Name, unique among live terminals: 1-32 of a-z 0-9 - _ ."`. The draft deterministic name `<projectKey>-<issue>-<role>-<attemptId>` in [docs/architecture.md](../architecture.md) uses a 16-character `projectKey`, 11 characters for `implementer`, and 3 hyphens (`30` characters before `<issue>` and `<attemptId>`). It exceeds 32 characters whenever `<issue>` and `<attemptId>` together exceed 2 characters. Slice 3 must shorten the name format to stay within `1-32` characters of `a-z 0-9 - _ .` (for example `<projectKey8>-<issue>-<roleCode>-<attemptId>`).
- **`hc label` filtering:** Not observed in live commands (see `Not observed`). `hc schema --json` documents `terminal.label` (`key=value`, free-form, never interpreted) and `terminal.list` `labels` filtering.

### Full-screen history-read side effect (note `N3` alone)

Note `N3` rests on the Captain's ordinary-use record; exact `hc read` commands, `N` values, raw outputs, and process exit codes were not saved as receipt files.

- Three times in this run, `hc read <t> --lines N` with `N > 0` on an idle terminal of agent program B left a mouse escape sequence typed into that program's prompt (`N3`).
- `hc schema --json` (`ReadResult.properties.how`) describes `"stitched"` as `"a full-screen app, read by scrolling it"`.
- Observed consequences (`N3`, `N2`): once the next `hc send` appended the task to that stray text; once `hc send` returned `started: false` and submitted nothing (`N2`, fifth bullet).
- Reads with `--lines 0` (screen only) on the same terminals were not followed by stray text in this run (`N3`).

### What this shows

- **Finished non-`--rm` persistence and listing:** In 3 of 3 finished non-`--rm` stand-in terminals present mid-run (`<prefix>-parent`, `<prefix>-plain`, `<prefix>-report`), `c8-ls-all` (`hc ls --all --json`, exit `0`) listed the finished terminal with `hidden_finished: 0`.
- **Full read when window is large enough:** In 1 of 1 finished non-`--rm` stand-in terminal (`c4-read-1000-json`), `hc read <report> --lines 1000 --json` returned all 401 lines (`report line 1 of 400` through `REPORT-END`) with `complete: true` and `how: "history"`.
- **Terminal dimensions and line-count inference:** The raw output of `c3-get-finished-by-address` recorded `rows: 120`, `cols: 200`, and `screen: "exact"` (matching `rows: 120` in 6 of 6 agent terminals in `e2-get-own-1` to `e2-get-own-6` and the default headless size of 200 by 120 in `hc schema --json` `terminal.run` `size`). `c7-read-0-text` (`hc read <report>`) returned `120` lines, and `c5`/`c6` (`--lines 50`) returned `170` lines. Explaining `170` lines as `120` screen rows plus `50` history lines is an **inference** from those counts and `terminal.read`'s `lines` description (`"Lines of history above the screen."`), not a breakdown reported directly by `hc read`.
- **`complete: true` does not prove the whole report was returned (design change needed):** In `c5-read-50-json`, lines 1 to 231 of the 400-line report were missing, yet `hc read` still returned `complete: true`. `hc schema --json` (`ReadResult.properties.complete`) defines `complete` as `"False when part of what was asked for may be missing."` It signals only whether the requested slice could be fetched (for instance, `hc --skill` and `ReadResult.properties.why` note that reading history while a full-screen app is `working`, `blocked`, or `error` returns only the screen with `complete: false` and `why` set to that status). Truncation caused by a too-small `--lines` bound is **not** flagged by `complete`.
- **Two design changes for capture and readback:**
  1. Never treat `ReadResult.complete === true` or a short line count as proof of a full report or verdict. Nothing in `c4`, `c5`, or `hc schema --json` shows that a short result holds the start of a verdict. After Captain absence, if a worker writes a report file (when writable, `hc --skill`), accept its verdict only after independent file checks. If a worker's verdict is on its screen only (section 7), do not accept a verdict found there after Captain absence. That holds even with `complete === true` and `Terminal.screen === "exact"`. Nothing ties that screen output to this attempt (issue `#27`), so it blocks the gates. The Captain then asks for a fresh authorized review and captures that verdict while present (section 7).
  2. Use `hc read --lines 0` (screen only) when inspecting live full-screen agent terminals that may receive later `hc send` calls (`N3`). Reserve `--lines N > 0` for finished terminals or terminals killed immediately after capture.
- **Not observed:** `ReadResult.complete: false`, `Terminal.screen: "inexact"`, and `hc read` on a finished full-screen agent terminal (see `Not observed`).

### Exact field comparison (`hc` `0.1.22`, step `e1-schema`)

| Surface | Schema | `turn` | `status` | Other key status/delivery fields |
|---|---|---|---|---|
| `hc get --json` | `Terminal` | `uint64` (``"Goes up each time the status leaves `working`."``) | `null` or `Status` object (`{ state, app?, kind?, msg?, progress?, title? }`) | `state` (`"live"` or `"finished"`), `reported` (`boolean`), `exit_code`, `signal`, `reason`, `first_message` (unsent template message only) |
| `hc send --json` | `SendResult` | `uint64` (`"The turn when the text went in."`) | `string \| null` (`"The program's status word when the text went in (null: it never said)."`) | `started` (`boolean \| null`: ``"Whether it went `working` within a few seconds; null when it doesn't report status, so nobody can tell."``), optional `wait` (`WaitResult \| null`) |
| `hc keys` (`terminal.keys`) | `KeysResult` | `uint64` | `string \| null` | Seen as string `status: "blocked"` with an integer `turn` in 3 of 3 clears in `N1` (note alone) and in 1 of 1 in `N5` (`hc keys <t> enter`, exit `0`) |

### What this shows

- **`status` has different types across commands:** `hc get --json` returns `status` as a JSON object (`status.state`, plus `app`, and `kind`/`msg` when blocked) or `null` for plain programs (`a2`, `e2-get-own-1` to `-6`, `N5`; `hc schema --json` `Status`). `hc send --json` returns `status` as a plain string word or `null` (`a5`, `N1`, `N2`, `N5`, `N7`; `hc schema --json` `SendResult`). Adapter code must read `status?.state` on `hc get` and never compare the `hc get` object directly to `"blocked"`.
- **Turn timing and attribution require a design change for ambiguous-send readback:** In the 5 `started: true` agent sends in note `N2` (plus `a5`/`a6` on a plain program), the send receipt's `turn` matched `hc get` in 2 of 2 pre-send checks and 4 of 4 during-turn checks. After the turn ended, `hc get` showed `turn + 1` in 3 of 3 post-turn checks. That matches `hc schema --json` `Terminal.properties.turn` (``"Goes up each time the status leaves `working`."``).
  - **Attribution gap:** A higher `turn` shows only that a turn left `working`, **not** which input moved the counter. An already-running turn can finish and move `turn`. Input from another sender, such as a reply from the worker's own child, can also move `turn`. `N2` shows when the counter moves, not which input moved it. P3 has no sample testing send-to-turn attribution (see `Not observed`).
  - **Required design change:** Never resend on an ambiguous send. `turn` movement never settles the attempt. The design defines no way yet for a worker to see or return an `attemptId`, and `hc` `0.1.22` has no field for it (`hc schema --json`; tracked in issue `#27`). Read `hc get --json` and screen-only `hc read --lines 0` once for the record. Stay `uncertain` and escalate.
- **`started: false` and `started: null` stay ambiguous:** `started: null` occurred in 1 of 1 send to a plain program (`a5-send-plain`). In note `N2`, `started: false` occurred when text failed to land on `done` (3 of 3 early sends on agent program A) and when stray prompt text blocked submission (1 send on agent program B, `N2`/`N3`). Later, 2 of 2 sends on `done` to agent program A returned `started: true`. For `started: false` or `started: null`, read `hc get --json` and `hc read --lines 0` once for the record, never resend, stay `uncertain`, and escalate.

## Open design questions for the repository owner

These are design decisions for the owner, not observation gaps:

1. **Launch-time folder-trust dialog (Behaviour 7):** Should a launch-time folder-trust dialog (`status.state === "blocked"`, `kind === "permission"`) for a worktree the Captain created be cleared as launch readiness after reading the screen (`hc read --lines 0`) and confirming the worktree path and prompt text? Every other `blocked` prompt would still escalate to the user. The alternative is to keep escalating every `blocked` prompt, including worktree folder-trust dialogs.
2. **How a worker sees an `attemptId` and returns it (issue `#27`; Behaviours 2, 4, and 5):** The design puts `attemptId` on commit records, but defines no way yet for a worker to see or return it. `hc` `0.1.22` has no field for it (`hc schema --json`). Decide how a worker receives and returns `attemptId` on launches, follow-up sends, and captured verdicts. Until then, ambiguous launches, ambiguous sends, and screen-only verdicts found after Captain absence do not settle on their own; they stay `uncertain` (or block the gates) and escalate.
