## Method

Probe P3 ([docs/probes/p3.md](p3.md)) showed that a scratch `hc` core cannot be kept safely apart from a live core on the same machine. Probe P5 therefore split into two parts: offline tracer code and tests against a fake `hc` (part 1, in [probes/p5/README.md](../../probes/p5/README.md)), followed by one live run against real `hc` `0.1.22` (part 2, recorded here).

With the repository owner's go-ahead on 2026-11-28, a separate operator ran one script once on a clean checkout at `f35ed10bebec3c6badf79b3e8e3abfe908ec9638`. The Captain wrote the script. Before the live run, the whole script ran against the repository's fake `hc`, and `77` of `77` checks held. A GPT advisor checked three earlier versions of the script and asked for changes each time. The version that ran holds those changes, though the advisor did not review that final version.

The live run used stand-in programs only. The stand-in controller is `probes/p5/tracer.mjs`, and the worker is a shell loop (`probes/p5/capture.mjs`) that waits at a named pipe (the gate), then prints `250` lines and writes a report file. No Pi session was started or reloaded.

### Preflight, bounding, and teardown

- **Preflight checks (all passed):**
  - `hc --version` exited `0` with output `hc 0.1.22` (matching the version whose shapes the probe uses).
  - `bun --version` exited `0` with output `1.4.0`.
  - Prefix inventory (`hc ls --all --json` filtered by `<prefix>-`) found `0` terminals before the run.
- **Prefix and state isolation:** One random 12-hex-character prefix (`<prefix>`) tagged every terminal name. Three cases ran in order: Case A (`run-a`), Case B1 (`run-b1`), and Case B2 (`run-b2`). Each case used a fresh state root (`<out>/<case>/state`), so each owner lease moved from epoch `1` on `start` to epoch `2` on `recover` and epoch `3` on `cleanup`.
- **Per-case sequence:** Each case ran `start` with `--crash-at` (controller kills itself with `SIGKILL`, exit `137`) and listed terminals via `hc ls --all --json` filtered by prefix. When a worker launched (cases A and B2), the script also ran `hc get <name> --json`. Case A then opened the gate; every case ran `recover`, an inventory check, `cleanup`, another inventory check, and readback by address. In Case B1 no worker launched. In Case B2 the gate stayed shut and `cleanup` ended the live worker.
- **Transient scopes and watchdogs:** Each of the `9` tracer calls (`start`, `recover`, `cleanup` in 3 cases) ran in a transient systemd scope with a runtime limit and stopped the scope on return. All `9` stops exited `5` (the scope had already ended), leaving nothing on the caller's side. Each case started a watchdog in its own session (`active`) set to open the gate and remove the case's terminal after `240` seconds. None fired; all three stopped (`exit 0`, ended `inactive`) after cleanup.
- **End-of-run and independent readback:** The script closed with `0` terminals carrying `<prefix>-` and exit `3` (not found) on address readback for `<address-1>` and `<address-2>`. Overall script result: `77` checks, `0` failed, exit `0`. Afterward, the operator and then the Captain independently read back `0` terminals carrying `<prefix>-` in `hc ls --all --json`, exit `3` from `hc get` for both addresses, no scope and no process left, and the checkout unchanged.

All raw receipts stay private. Every path, name prefix, project key, terminal name argument, and terminal address is replaced with the sanitised record's placeholders: `<hc>`, `<out>`, `<prefix>`, `<projectKey>`, `<name>`, `<address-1>`, and `<address-2>`.

The sanitised live-run record (`run-1-sanitised.log`) and the method note (`run-1-method.md`) also stay with the owner, outside this repository. Line numbers cited below serve the owner's audit, and every command, exit code, count, event list, and field value relied on is reproduced here.

## Limits

1. **Stand-ins only:** The "Captain" is the tracer's controller process, and the worker is a shell loop. No Pi session was started or reloaded. This is proof for the tracer, not for real Pi reload wiring.
2. **One live run:** Each case ran once, on one machine, on `hc` `0.1.22` (with Bun `1.4.0`).
3. **Basis for "no second worker":** That claim rests on `1` `launch_intent` record in each case's commit log and on equal prefix-filtered `hc ls --all --json` inventories before and after recovery. Two listings cannot show a terminal that appeared and vanished between them.
4. **Plain-program `status` and `turn`:** A plain program shows `status: null` and `turn: 0` in `hc get`. This live run says nothing about the status values of an agent program.
5. **External bound on the gate read:** The stand-in worker's read at the named pipe gate has no time limit of its own. The script bounded it from outside with watchdogs (`240` seconds) and transient systemd scopes.
6. **Case A completion order:** In Case A the worker finished because the script opened the gate after the controller died. "The worker finishes while the controller is away" is shown for that order only. Because the gate opened before `recover` ran and internal `hc` calls are not logged, the record does not show whether the worker finished before `recover`'s `hc get` or while `hc wait` was running.
7. **`hc kill` and `hc rm` outputs unread:** The tracer reads only exit codes from `hc kill` and `hc rm`. Their output fields were not read.
8. **Final script not advisor-reviewed:** A GPT advisor checked three earlier versions of the live-run script and asked for changes each time. The version that ran holds those changes, but the advisor did not review that final version (`run-1-method.md`).
9. **Sanitised summary log only:** The sanitised record captures script commands, tracer JSON outputs, event-name lists, inventories, and check verdicts. Raw `hc` sub-command transcripts inside `tracer.mjs`, raw commit record JSON bodies (`prevRecordSha256` hash chains), and Case B2's screen-readback artifact hash are not in the sanitised record.
10. **Timeout and watchdog fault paths not tripped:** All `9` stops of transient systemd scopes exited `5` (command already ended), and none of the three watchdogs fired. Neither timeout enforcement nor watchdog teardown ran under fault in live use.
11. **Absolute paths only in the live script:** The method note (`run-1-method.md`, added 2026-11-28) states that the operator gave one absolute output folder, shown in the record as `<out>`. The script built every path it gave to the tracer (`--state-root`, `--cwd`, `--report-file`, `--gate-fifo`) under that folder, so each path was absolute. The sanitised record itself cannot show whether a path was absolute. Relative path handling when start, worker, and recovery use three separate folders was tested offline in `probes/p5/p5.test.mjs`, not in this live run.

## Not observed

The items below were not observed in this live run and are not assumed:

- Real Pi `/reload` wiring, real Pi session recovery, or killing a real Captain session.
- Real agent templates, non-null `status` objects (`working`, `blocked`, `idle`, `done`), non-zero `turn`, or retained `first_message.sent: false` on live `hc`.
