## Checks 3 and 4: Fabric provider seam, withdrawal, and real reload

### How the probe ran without credentials or model turns

`probes/p1/run.sh` installed real `npm:pi-fabric@0.140.1` and local `<worktree>` into two isolated scratch fixtures in opposite install orders:

- **Order A (`fabric-first`):** `pi-fabric` `0.140.1` first, then `herdr-captain`.
- **Order B (`captain-first`):** `herdr-captain` first, then `pi-fabric` `0.140.1`.

For each fixture, `probes/p1/probe-fabric.ts` loaded both extensions through Pi's real `DefaultResourceLoader`, `createAgentSession`, `SessionManager.inMemory()`, and `session.bindExtensions({})`. Passive counters watched Pi's real `eventBus` with no stubs or mocks.

To run Fabric programs with zero credentials and zero model turns, the probe emitted `pi-fabric:program:run:v1` on the real event bus. `pi-fabric` ran the guest TypeScript in its QuickJS sandbox and returned the result through the reply callback.

To run a real reload without an interactive terminal, the probe called `session.reload()` (`AgentSession.reload()` in `@earendil-works/pi-coding-agent`). Interactive `/reload`, RPC mode, and print mode call the same method.

## Findings against ADR-0001 and ADR-0004

### ADR-0001 (Direct Fabric provider boundary)

1. **Direct registration holds. No `pi.registerTool()` fallback is needed.** On `pi-fabric` `0.140.1`, `fleet` is not a reserved provider name. It gets a `fleet` global inside Fabric programs, checks closed schemas (`additionalProperties: false`), withdraws cleanly, and reloads with zero duplicate handlers. ADR-0001's revisit rule does not trigger.
2. **Use v1 event channel strings instead of importing `pi-fabric/protocol` at runtime.** Pi loads installed packages with separate module roots (Pi `docs/packages.md`). A runtime import of `pi-fabric/protocol` in `src/index.ts` would fail in local-path or git installs unless `herdr-captain` added `pi-fabric` to `dependencies`. Putting the v1 strings (`pi-fabric:provider:register:v1`, `pi-fabric:provider:discover:v1`, `pi-fabric:provider:withdraw:v1`) directly in `src/index.ts` keeps zero runtime dependencies and respects package boundaries.
3. **`pi-fabric` `0.140.1` load-order withdrawal quirk requires registering on `session_start`.** In `pi-fabric` `0.140.1`, `FabricRuntimeState.initialize` handles `FABRIC_PROVIDER_DISCOVER_EVENT` by calling inner `FabricRuntimeState.registerExternal`. That path does not update outer `FabricState.#externalProviders`. Outer `FabricState.withdrawExternal` checks `this.#externalProviders.has(name)` before forwarding a withdrawal. If `herdr-captain` loads before `pi-fabric` and emits `FABRIC_PROVIDER_REGISTER_EVENT` only in its factory (as `pi-fabric/docs/providers.md` shows), `pi-fabric` is not yet listening. `fleet` then registers only through discovery, and later `FABRIC_PROVIDER_WITHDRAW_EVENT` calls return `false`. Emitting `FABRIC_PROVIDER_REGISTER_EVENT` with `overwrite: true` in both the factory and `session_start` updates outer `FabricState` in both load orders. Slice 4 must keep this pattern.
4. **SDK probe host resolution.** When `pi-fabric` `0.140.1` runs under a Pi SDK script instead of the `pi` binary, `loadHostSdk()` walks `node_modules` above `process.argv[1]` for `@earendil-works/pi-coding-agent`. `probes/p1/run.sh` stages `probe-fabric.ts` in `<scratch>/probe-host/` with a symlink to the host's Pi package. That keeps `node_modules` out of this repository.

### ADR-0004 (Standalone package and pinned consumption)

1. **Zero-dependency manifest passes offline local-path parity.** `package.json` sets `keywords: ["pi-package"]`, `pi.extensions: ["./src/index.ts"]`, a peer dependency on `@earendil-works/pi-coding-agent`, and no runtime `dependencies`. Local-path `pi install` exits `0` both online and inside `unshare -rn`.
2. **Local-path installs write relative paths in `settings.json`.** `pi install <abs-path>` stores a path relative to `<agentDir>/settings.json`. `pi list` prints both that relative entry and the resolved full path. Offline fixtures that read `settings.json` must expect relative paths.
3. **Pinned git install check is ready but unproven until push.** Pi `1.6.1` (`package-manager.js`) clones `git:github.com/ryan-brosas/herdr-captain@<sha>` into `<agentDir>/git/github.com/ryan-brosas/herdr-captain`, checks out `<sha>`, and runs dependency install (`--omit=dev --omit=peer`) when `package.json` exists. With zero runtime `dependencies`, `herdr-captain` needs no npm fetch. Check 5 stays `PENDING CAPTAIN PUSH` until the commit is on GitHub.
