## Environment and fixture isolation

- **Tools observed:** `pi` `1.6.1` (`@earendil-works/pi-coding-agent`), `pi-fabric` `0.140.1`, `bun` `1.4.0`, `npm` `12.2.1`, `git` `2.56.0`.
- **Package under test:** `package.json` (`name: "herdr-captain"`, `version: "0.1.0"`, zero runtime `dependencies`) and `src/index.ts` (direct Fabric provider `fleet` with one read-only action `status`). Both files are byte-identical to pinned commit `7fc96329add1d7604a27122e235acbbf04a78095`.
- **Single allowlisted environment (`env -i`) and scratch `cwd`:** `probes/p1/run.sh` creates `<scratch>` with `mktemp -d /tmp/herdr-captain-p1.XXXXXX` and removes it on `EXIT`, `INT`, `TERM`, and `HUP`. Every `pi` command, `bun` invocation, `git` check, and SDK session runs from an empty `<scratch>/cwd` directory, and every `bun` call passes `--no-env-file` to disable automatic `.env` loading. Every fixture command runs through `run_with_allowlisted_env`, which starts from an empty environment (`env -i`) and passes only 15 keys: `PATH`, `HOME=<scratch>/home`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `TMPDIR`, `LANG=C.UTF-8`, `LC_ALL=C.UTF-8`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_TERMINAL_PROMPT=0`, `PI_CODING_AGENT_DIR`, `PI_SKIP_VERSION_CHECK=1`, and `BUN_INSTALL` (host Bun root so the `pi` launcher finds `bun`). Because `HOME`, `XDG_*`, and `cwd` all stay inside `<scratch>` and `--no-env-file` is set, host credential files (such as `~/.pi/agent/auth.json`, `~/.aws`, `~/.config/gcloud`, or `~/.netrc`) and caller or repository `.env` files stay unreachable.
- **Per-command isolation assertion:** Every `pi` invocation in `probes/p1/run.sh` runs through `run_fixture_cmd` (Checks 1, 3, 4, and 5) or `run_offline_fixture_cmd` (Check 2 inside `unshare -rn`). Before each `pi` command and before `probe-fabric.ts`, the wrapper calls Pi's own `getAgentDir()`, `os.homedir()`, and `process.cwd()` under the same `env -i` allowlist with `bun --no-env-file`. It prints `Resolved Pi getAgentDir()=...`, asserts all three paths stay inside `<scratch>`, and asserts `<agentDir>/auth.json` is absent. Both wrappers explicitly propagate assertion failures (`|| return $?`) rather than relying on `errexit`, so a failed guard still blocks the fixture command inside `$(...)` command substitutions.
- **SDK runtime and protocol checks:** Before loading Pi, `probes/p1/probe-fabric.ts` asserts `process.env` holds only allowlisted keys and both `os.homedir()` and `process.cwd()` resolve inside `<scratch>`. It then asserts `piSdk.getAgentDir()` inside `<scratch>`. After `createAgentSession()`, it audits Pi's `ModelRuntime` over all 45 builtin providers (`getAvailableSnapshot()`, `hasConfiguredAuth()`, and `checkAuth()`). It asserts zero available models, zero configured providers, sentinel `session.model` (`unknown/unknown`), and a non-empty `modelFallbackMessage`. It also imports installed `pi-fabric`'s `./protocol` export and `<package>/src/index.ts`, failing if `FABRIC_PROVIDER_REGISTER_EVENT`, `FABRIC_PROVIDER_DISCOVER_EVENT`, or `FABRIC_PROVIDER_WITHDRAW_EVENT` drift.
- **Path sanitization:** `<scratch>` replaces the temporary `mktemp -d` directory. `<worktree>` replaces the local checkout path. `<rel-worktree>` replaces the relative path Pi writes into `settings.json`. Git clone `\r` progress redraws are collapsed to final lines and trailing spaces are trimmed. All other lines are verbatim output.

## Checks 3 and 4: Fabric provider seam, withdrawal, and real reload

### How the probe ran without credentials or model turns

`probes/p1/run.sh` installed real `npm:pi-fabric@0.140.1` and local `<worktree>` into two isolated scratch fixtures in opposite install orders:

- **Order A (`fabric-first`):** `pi-fabric` `0.140.1` first, then `herdr-captain`.
- **Order B (`captain-first`):** `herdr-captain` first, then `pi-fabric` `0.140.1`.

For each fixture, `probes/p1/probe-fabric.ts` loaded both extensions through Pi's real `DefaultResourceLoader`, `createAgentSession`, `SessionManager.inMemory()`, and `session.bindExtensions({})`. Passive counters watched Pi's real `eventBus` with no stubs or mocks.

To run Fabric programs with zero credentials and zero model turns, the probe emitted `pi-fabric:program:run:v1` on the real event bus. Because the `env -i` allowlist strips `PI_FABRIC_*` variables, `pi-fabric` used its default `typescript` kernel, ran the guest TypeScript in QuickJS, and returned the result through the reply callback.

To run a real reload without an interactive terminal, the probe called `session.reload()` (`AgentSession.reload()` in `@earendil-works/pi-coding-agent`). Interactive `/reload`, RPC mode, and print mode call the same method.

### Exact provider invocations tested

1. Direct withdrawal: emit `pi-fabric:provider:withdraw:v1` with `{ name: "fleet" }`, then check `tools.providers()`, `tools.search({ query: "fleet" })`, `tools.list({ provider: "fleet" })`, `tools.call({ ref: "fleet.status", args: {} })`, and `typeof globalThis.fleet`.
2. Post-withdrawal reload: call `session.reload()` and confirm `fleet` restores cleanly with one discovery response.

Unload + reload: remove `herdr-captain` from `<scratch>/<agent>/settings.json`, call `session.reload()`, verify `session_shutdown` emits one withdraw event, verify `pi-fabric` discovery gets zero `fleet` responses, and confirm `fleet` is gone from `tools.providers()`, `tools.call(...)`, and `globalThis.fleet`.

## Findings against ADR-0001 and ADR-0004

### ADR-0001 (Direct Fabric provider boundary)

1. **Direct registration holds. No `pi.registerTool()` fallback is needed.** On `pi-fabric` `0.140.1`, `fleet` is not a reserved provider name. It gets a `fleet` global inside Fabric programs, checks closed schemas (`additionalProperties: false`), withdraws cleanly, and reloads with zero duplicate handlers. ADR-0001's revisit rule does not trigger.
2. **Use v1 event channel strings instead of importing `pi-fabric/protocol` at runtime, and check them against installed `pi-fabric` in tests.** Pi loads installed packages with separate module roots (Pi `docs/packages.md`). A runtime import of `pi-fabric/protocol` in `src/index.ts` would fail in local-path or git installs unless `herdr-captain` added `pi-fabric` to `dependencies`. Putting the v1 strings (`pi-fabric:provider:register:v1`, `pi-fabric:provider:discover:v1`, `pi-fabric:provider:withdraw:v1`) in `src/index.ts` keeps zero runtime dependencies, while `probe-fabric.ts` imports installed `pi-fabric`'s `./protocol` export to fail fast on any future constant drift.
3. **`pi-fabric` `0.140.1` load-order withdrawal quirk requires registering on `session_start`.** In `pi-fabric` `0.140.1`, `FabricRuntimeState.initialize` handles `FABRIC_PROVIDER_DISCOVER_EVENT` by calling inner `FabricRuntimeState.registerExternal`. That path does not update outer `FabricState.#externalProviders`. Outer `FabricState.withdrawExternal` checks `this.#externalProviders.has(name)` before forwarding a withdrawal. If `herdr-captain` loads before `pi-fabric` and emits `FABRIC_PROVIDER_REGISTER_EVENT` only in its factory (as `pi-fabric/docs/providers.md` shows), `pi-fabric` is not yet listening. `fleet` then registers only through discovery, and later `FABRIC_PROVIDER_WITHDRAW_EVENT` calls return `false`. Emitting `FABRIC_PROVIDER_REGISTER_EVENT` with `overwrite: true` in both the factory and `session_start` updates outer `FabricState` in both load orders. Slice 4 must keep this pattern.
4. **SDK probe host resolution.** When `pi-fabric` `0.140.1` runs under a Pi SDK script instead of the `pi` binary, `loadHostSdk()` walks `node_modules` above `process.argv[1]` for `@earendil-works/pi-coding-agent`. `probes/p1/run.sh` stages `probe-fabric.ts` in `<scratch>/probe-host/` with a symlink to the host's Pi package. That keeps `node_modules` out of this repository.
5. **Non-`typescript` Fabric kernel sessions (finding O1).** An operator rerun of the earlier harness from a Fabric child session failed Checks 3, 4, and 5 with `startup: status program failed: This session's kernel is python; caller-supplied code runs only in the typescript kernel`. The confirmed cause is inherited `PI_FABRIC_KERNEL=python`: `pi-fabric` `0.140.1`'s `resolveFabricConfig` reads `process.env.PI_FABRIC_KERNEL` into `executor.kernel`, and `runHostProgram` (`dist/programs/host.js`) rejects caller-supplied inline `code` on `pi-fabric:program:run:v1` whenever `kernel !== "typescript"`. Reproducing `PI_FABRIC_KERNEL=python` against the prior revision produced that exact error; isolating the harness with `env -i` eliminated it. For a package loaded inside a non-`typescript` session, `pi-fabric` `0.140.1` docs and runtime (`docs/providers.md`, `dist/runtime/monty-runtime.js`) show two consequences:
   - Direct provider registration (`register:v1`, `discover:v1`, `withdraw:v1`) is kernel-agnostic and exposes provider globals (`fleet`) and `tools.*` in Python kernels as well as TypeScript kernels. However, Python guest programs are not statically type-checked, so enforcement depends on dispatch-time JSON Schema validation and the provider's own `invoke()` checks (both already present in `src/index.ts`, and required for Slice 4).
   - Host-invoked inline programs via `pi-fabric:program:run:v1` fail outside the `typescript` kernel. Probes or host tools that rely on inline `pi-fabric:program:run:v1` must isolate `PI_FABRIC_*` or run in a `typescript`-kernel session.
   - Scope note: Probe P1 reproduced the `PI_FABRIC_KERNEL=python` rejection of inline `pi-fabric:program:run:v1` live, and verified Python-kernel provider exposure from `pi-fabric` `0.140.1` source and docs, but did not run a live Python-kernel invocation of `fleet.status()`.

### ADR-0004 (Standalone package and pinned consumption)

1. **Zero-dependency manifest passes offline local-path parity.** `package.json` sets `keywords: ["pi-package"]`, `pi.extensions: ["./src/index.ts"]`, a peer dependency on `@earendil-works/pi-coding-agent`, and no runtime `dependencies`. Local-path `pi install` exits `0` both online and inside `unshare -rn`.
2. **Local-path installs write relative paths in `settings.json`.** `pi install <abs-path>` stores a path relative to `<agentDir>/settings.json`. `pi list` prints both that relative entry and the resolved full path. Offline fixtures that read `settings.json` must expect relative paths.
3. **Pinned git SHA install holds end-to-end.** `pi install git:github.com/ryan-brosas/herdr-captain@7fc96329add1d7604a27122e235acbbf04a78095` cloned into `<agentDir>/git/github.com/ryan-brosas/herdr-captain` and detached `HEAD` at the exact SHA. The post-clone install step printed `up to date in 182ms` with no packages added. That points to zero npm registry fetches for `herdr-captain` (inferred from the zero-dependency manifest rather than packet capture). Every `fleet` provider check on `pi-fabric` `0.140.1` passed, so ADR-0004's revisit rule does not trigger.
