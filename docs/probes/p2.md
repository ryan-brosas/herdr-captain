# Probe P2: Owner lease lifecycle faults

**Status:** COMPLETE. The holder-process owner lease in [architecture.md](../architecture.md) section 5 works on Linux under Bun. Every rule from **(a)** through **(f)** needs a small design refinement before Slice 1 builds on it.

Terms follow [CONTEXT.md](../../CONTEXT.md). Related decisions live in [0002-recovery.md](../adr/0002-recovery.md).

## Runtime and host environment

How `pi` starts on this host was checked directly rather than assumed:

- The `pi` launcher runs `bun --no-env-file <pi-bin> "$@"`.
- The installed Pi package (`@earendil-works/pi-coding-agent` `1.6.1`) loads TypeScript extensions in-process via `jiti` with `moduleCache: false`. Each `/reload` evaluates a new module instance inside the same Bun process while sharing `globalThis`.
- Probe runtime and host tools:
  - JavaScript runtime: `bun 1.4.0` (standard library `node:*` APIs only, zero external dependencies)
  - Lock binary: `flock from util-linux 2.42.4`
  - Git binary: `git version 2.56.0`
  - Platform: `Linux x64` (exact kernel release omitted from runner output and public docs)

Every run wrote only inside `<scratch>` folders made with `mktemp` under `/tmp` and removed on exit. All three runners (`run.mjs`, `diagnose-design-gaps.mjs`, and `negative-controls.mjs`) register `uncaughtException` and `unhandledRejection` handlers to print the original error, stop tracked processes, remove their scratch folder, and exit non-zero, plus a synchronous `exit` fallback. Only `run.mjs` is exercised by `ctrl-9`; `diagnose-design-gaps.mjs` and `negative-controls.mjs` carry the same handler pattern with no automated control. In `run.mjs`, the `flock` waiter in `waitForKernelLockRelease` is outside the `ownedChildren` cleanup registry.

## Probe implementation

- [probes/p2/lease.mjs](../../probes/p2/lease.mjs): owner lease holder, atomic `owner.json` fencing epoch, per-project serialized queue, and revocation drain. It also handles synchronous `/proc/<pid>/stat` holder checks with `starttime` identity, `/proc/<pid>/environ` token cleanup helpers, the process-global `Symbol.for(...)` map, and `git rev-parse --git-common-dir` keys.
- [probes/p2/owner-worker.mjs](../../probes/p2/owner-worker.mjs): separate Bun worker process for multi-process contention, `SIGKILL`, and post-acquisition detached child checks. It binds raw-handle child cleanup right after `spawn(...)`, before fallible stat inspection or PID-file publication.
- [probes/p2/run.mjs](../../probes/p2/run.mjs): runner script for checks 1 to 6 using real processes, real `flock`, and no sleep synchronization. It assigns a unique `HERDR_P2_CHILD_TOKEN` before spawning Check 5's worker so cleanup stops detached children even if the worker dies before publishing anything, as long as `/proc` and target process environments can be read. When they cannot be read, the sweep finds no matches and cleanup reports success. It exits non-zero if any check fails.
- [probes/p2/negative-controls.mjs](../../probes/p2/negative-controls.mjs): runnable negative-control suite that mutates scratch copies under `/tmp` only (never committed files) and checks expected failure causes scoped to each target check block. Controls `ctrl-4a` and `ctrl-4b` match the same pre-effect dead-holder rejection message and cannot tell their two mutations apart. On controller timeouts, it stops tracked children, sweeps detached descendants by token where `/proc` and process environments can be read, and removes scratch folders. It exits `0` only when every control passes.
- [probes/p2/diagnose-design-gaps.mjs](../../probes/p2/diagnose-design-gaps.mjs): runnable checks that reproduce three design gaps in section 5 (`--no-fork`, `--conflict-exit-code`, and awaiting holder exit on close).

## Check-by-check notes

1. **Check 1 (Second owner conflict):** A second Bun process failed right away with `owner_conflict` (exit `2`). The `owner.json` SHA-256, inode, and mtime did not change. Owner 1 kept its lease and finished a queued write afterward.
2. **Check 2 (`SIGKILL` release timing):** Sending `SIGKILL` to owner 1 closed its stdin descriptor and caused holder 1 to exit. Kernel lock release took `2.35ms`, `2.3ms`, and `2.14ms` in three consecutive runs, timed by a blocking `flock --exclusive --timeout 5` wait with no sleep polling. Owner 2 acquired on its first `--nonblocking` try (`28.88ms` total in Run 1 including Bun startup), bumped `owner.json` from epoch `1` to `2`, and blocked owner 3 with `owner_conflict`. A restarted owner arriving during that ~2ms teardown window fails closed with `owner_conflict` rather than stealing the lease.
3. **Check 3 (Simulated reload in one process):** **Simulated reload only; real Pi `/reload` is another ticket (Probe P1).** Bun `1.4.0` strips query strings from `file://` ESM URLs, so `import("./lease.mjs?reload=2")` returns the cached module. The probe copies `lease.mjs` to distinct `<scratch>` paths to force fresh module evaluations and confirms distinct `MODULE_INSTANCE_ID` values and distinct `LeaseError` constructors. All 12 consecutive reloads handed off through the `Symbol.for(...)` registry on `globalThis` with no sleeps. Prior holders exited each time, and stale calls on instance 1 rejected with `lease_revoked`. **Scope limit:** This simulated reload excludes Pi/`jiti` lifecycle wiring, withdrawal handlers, and reload while old queued work is still in flight.
4. **Check 4 (Withdrawal with queued work, unreaped zombie holder, and epoch drift):** Item 0 ran its authorized write, then paused at a promise barrier before its effect check while items 1 to 3 queued behind it. Calling `revoke()` set `revoked = true` first, before drain began. While paused, an external process still hit `owner_conflict`, showing the holder kept the lock during drain. Opening the barrier rejected item 0's effect and items 1 to 4 (including item 4 queued after `revoke()`) with `lease_revoked`. Neither `forbidden-write.marker` nor `forbidden-effect.marker` appeared.
   - **Deterministic unreaped zombie holder before exit callback:** Another sub-check sends `SIGKILL` to `holderPid` inside `write()` and blocks synchronously in `flock --exclusive --timeout 5` without yielding to the JS event loop. Before the pre-effect check runs, `revoked` is still `false`, `/proc/<holderPid>/stat` is state `Z` (dead unreaped zombie), and `kill(holderPid, 0)` still succeeds. The pre-effect `assertValid()` call catches `!isHolderAlive()` synchronously before any exit callback runs and prevents `effect` from writing its marker. Deleting `!isHolderAlive()` (`ctrl-4a`) or weakening it to `kill(pid, 0)` (`ctrl-4b`) both fail Check 4.
   - **Epoch drift before effect and before write:** Separate sub-checks drift `owner.json.epoch` both between an authorized `write()` and its `effect()` (blocking the effect with `lease_revoked`) and before `write()` (blocking both write and effect).
5. **Check 5 (Post-acquisition child non-inheritance):** `/proc/self/fdinfo` in owner 1 showed Bun opened holder stdio as Unix `socketpair` descriptors with `O_CLOEXEC` (`flags=02004002`). A detached `sleep 60` child started after acquisition had only `/dev/null` on fds 0 to 2 and zero inherited parent targets or socket/pipe descriptors. After `SIGKILL` of owner 1, the kernel lock released (`2.14ms`, `2.13ms`, and `1.86ms` in three runs) and owner 2 acquired epoch `2` while the detached child stayed alive. **Scope limit:** This CLOEXEC evidence covers only the tested `node:child_process.spawn` configuration. Explicit numeric-FD or holder-stream forwarding through child `stdio` can still preserve the pipe, and other runtime launch APIs (such as `Bun.spawn`) were not exercised.
6. **Check 6 (Linked worktree contention):** Two differently named linked worktrees (`wt-alpha` and `completely-different-name`), a symlink (`wt-beta-symlink`), and `main-clone` all resolved `realpath(git rev-parse --git-common-dir)` to one 16-hex `projectKey` (`7f700d8111abcd3a` in Run 1) and contended for one owner lease. A separate clone hashed to `708e8cf10e5ad4a3` and acquired on its own.

## Verdicts for section 5 rules (a) to (f)

| Rule | Verdict | Smallest design change |
|---|---|---|
| **(a) No stealing** | Needs a design change | Pass `--nonblocking` and `--conflict-exit-code 200` to `flock`, and forbid unlinking `owner.lock`. |
| **(b) Fencing epoch** | Needs a design change | Pass `--no-fork` (`-F`) to `flock` with a non-forking holder (`exec`), and close plus await holder exit on `owner.json` failure. |
| **(c) Serialized queue** | Needs a design change | Define "holder alive" synchronously via `/proc/<holderPid>/stat` (rejecting `Z`/`X`/`x` states and checking `starttime`), not async exit callbacks or `kill(pid, 0)`. |
| **(d) Revocation drain** | Needs a design change | After closing holder stdin, await holder process exit (with a bounded `SIGKILL` fallback) before resolving revocation. |
| **(e) Reload cleanup** | Needs a design change | Store a revocation handle (`revokeAndClose(): Promise<void>`) on the `Symbol.for(...)` global map, await it before acquiring, and compare-and-delete on exit. |
| **(f) Non-inheritance** | Needs a design change | Forbid explicit numeric-FD or holder-stream forwarding in child `stdio`, keep a `/proc` and surviving-child test in Slice 1, and test any launch API other than `node:child_process.spawn` before adopting it. |

### Detailed rule rationale

- **(a) No stealing (needs a design change):** Kernel `flock` exclusion held in every cross-process and worktree check. Without `--conflict-exit-code`, `flock` exits `1` on conflict. That collides with a holder process exiting `1` before its ready line (`DIAG [gap-2]`). Passing `--conflict-exit-code 200` (outside `sysexits` 64 to 78 and shell codes 126 to 128) and `--nonblocking` separates `owner_conflict` from startup errors. Code must also never unlink `owner.lock` on release because unlinking splits the path onto a second inode.
- **(b) Fencing epoch (needs a design change):** Ready-line order, `projectKey` checks, monotonic `epoch`, and `temp -> fsync -> rename` plus directory `fsync` all worked under Bun `1.4.0`. Without `--no-fork`, `flock` forks `<holder>` so two PIDs hold `owner.lock` and `child.pid` is `flock` instead of `<holder>`. Killing `flock` while stdin stays open leaves `<holder>` alive still holding the lock (`DIAG [gap-1]`, which tests wrapper/holder PID divergence rather than owner-death EOF). Passing `--no-fork` with a non-forking holder (`sh -c 'printf "ready\n"; exec cat >/dev/null'`) keeps one PID (`child.pid === holderPid`). If `owner.json` validation or write fails after the ready line, acquire must close stdin and await holder exit before throwing.
- **(c) Serialized queue (needs a design change):** FIFO order, pre-write checks, and pre-effect checks worked on withdrawal, unreaped holder death, and epoch drift (both pre-effect after an authorized write and pre-write). However, section 5 leaves "holder alive" undefined. Check 4 and negative controls `ctrl-4a` and `ctrl-4b` show two Linux traps. First, a dead holder's async exit callback has not run before a synchronous pre-effect check (`revoked === false`). Second, `kill(holderPid, 0)` still succeeds on an unreaped zombie whose lock fd is already closed. Rule (c) must define holder liveness synchronously via `/proc/<holderPid>/stat`, rejecting `Z`, `X`, and `x` states and checking process `starttime` (paired with `--no-fork` from rule (b)).
- **(d) Revocation drain (needs a design change):** Setting `revoked = true` first and draining queued work before closing stdin blocked every post-revocation write and effect while keeping `owner.lock` held during drain (Check 4; broken in `ctrl-1`). Closing stdin alone does not free the lock immediately. In timing samples (`DIAG [gap-3]`), closing without awaiting holder exit hit `owner_conflict` `5/40` times in the recorded run (`3/40` to `15/40` in repeated runs), versus `0/40` asserted when awaiting holder exit with no sleep. Revocation must await holder exit (with a bounded `SIGKILL` fallback, safe once `--no-fork` is used) before resolving.
- **(e) Reload cleanup (needs a design change):** A `Symbol.for(...)` map on `globalThis` bridged separate module evaluations cleanly through 12 consecutive simulated reloads (Check 3; broken in `ctrl-2`). Storing only a raw holder pipe or child handle is not enough. Reload cleanup must set the old instance's `revoked` flag, drain its queue, close stdin, and await prior holder exit before starting a new `flock`. Cleanup on exit must compare-and-delete (`if (map.get(projectKey) === entry) map.delete(projectKey)`) so a late exit callback cannot erase the new instance's entry.
- **(f) Non-inheritance (needs a design change):** Under `bun 1.4.0`, the tested `node:child_process.spawn` configuration opens holder stdio as `O_CLOEXEC` Unix `socketpair` descriptors (`flags=02004002`). Detached children inherit none of them, and `SIGKILL` of the owner releases the lease while the child stays alive (Check 5). Because JS relies on runtime spawn defaults rather than calling `pipe2(O_CLOEXEC)` directly, rule (f) needs an explicit constraint. Extension code must never forward numeric file descriptors or holder stdio streams through any child's `stdio` array. Slice 1 should keep the `/proc` and surviving-child check, and test any other launch API (such as `Bun.spawn`) before adopting it.

## Scope limits and unproven items

- **Real Pi `/reload`:** Check 3 simulates reload by importing distinct scratch copies of `lease.mjs` inside one Bun process. It excludes Pi/`jiti` lifecycle wiring, withdrawal handlers, and reload with old queued work still in flight. Real Pi `/reload` belongs to Probe P1.
- **Other child launch APIs and stdio forwarding:** Check 5 exercises `node:child_process.spawn` with piped holder stdio and a detached child whose `stdio` is `["ignore", "pipe", "ignore"]`. It does not test `Bun.spawn` or explicit numeric-FD or stream pass-through.
- **Gap 1 owner-death EOF:** `DIAG [gap-1]` kills the `flock` wrapper while keeping stdin open via a FIFO writer; owner-death EOF is tested separately in Checks 2 and 5.
- **Gap 3 non-awaited arm count:** `DIAG [gap-3]` records OS-scheduling timing samples on the non-awaited arm and asserts only `0/40` conflicts on the awaited arm.

## Known limits

These probe-harness and negative-control limits are tracked in [#17](https://github.com/ryan-brosas/herdr-captain/issues/17). None of them changes the verdicts for section 5 rules **(a)** to **(f)** above, because those verdicts rest on the `flock`, `/proc`, reload-registry, and `O_CLOEXEC` behavior shown in Checks 1 to 6 and Diagnostics 1 to 3.

- **Fatal-error handler coverage and `flock` waiter:** `ctrl-9` exercises uncaught-error cleanup on `probes/p2/run.mjs` only. `probes/p2/diagnose-design-gaps.mjs` and `probes/p2/negative-controls.mjs` register the same handlers with no automated control. In `probes/p2/run.mjs`, the `flock` waiter in `waitForKernelLockRelease` is outside the `ownedChildren` cleanup registry.
- **Token cleanup needs readable `/proc`:** `HERDR_P2_CHILD_TOKEN` and `HERDR_P2_CTRL_TOKEN` sweeps read `/proc/<pid>/stat` and `/proc/<pid>/environ`. Where `/proc` or target process environments cannot be read, `findProcessesByEnvToken` returns no matches and `stopProcessesByEnvToken` reports success.
- **Shared failure matcher in `ctrl-4a` and `ctrl-4b`:** Controls `ctrl-4a` and `ctrl-4b` match the same Check 4 pre-effect dead-holder rejection message and cannot tell their two mutations apart.
- **No outer cleanup for `ctrl-5a` in-process lease:** Part 2 of `ctrl-5a` imports a mutated `lease.mjs` and calls `acquireLease` inside `negative-controls.mjs`. If the post-acquire cleanup under test fails, `ctrl-5a` has no outer cleanup of its own for that holder process.
